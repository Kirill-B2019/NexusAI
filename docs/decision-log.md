# NEXUS AI — Decision Log (ADR)

История архитектурных решений. Что выбрали, почему, какие альтернативы отвергли.

## ADR-001: Qwen3-4B Q4_K_M

**Дата:** 2026-10-04
**Статус:** принято

**Контекст:** сервер 6 ядер / 12 ГБ RAM, без GPU. Нужна модель, работающая с русским, кодом, аналитикой.

**Решение:** Qwen3-4B в квантовании Q4_K_M (~2.4 ГБ).

**Альтернативы:**
- **Qwen3-1.7B** — быстрее, но слабее по качеству
- **Qwen3-8B** — не влезает в RAM вместе с API/БД
- **Llama-3-8B** — хуже с русским
- **YandexGPT / GigaChat** — облако, не подходит по политике

**Компромисс:** ~5–7 ток/сек на CPU. Для интерактивных ответов приемлемо.

**Последствия:**
- thinking-режим работает, но 3–5 мин на запрос
- оркестрация 3+ экспертов — 4–8 минут
- при росте нагрузки — миграция на GPU (Этап 9)

## ADR-002: llama.cpp вместо vLLM

**Дата:** 2026-10-04
**Статус:** принято

**Контекст:** CPU-only инференс, нужна OpenAI-совместимая API.

**Решение:** llama.cpp (образ `ghcr.io/ggml-org/llama.cpp:server`).

**Альтернативы:**
- **vLLM** — GPU-only
- **Ollama** — обёртка над llama.cpp, менее гибкая
- **TGI** — тяжёлый, для прод-нагрузок

**Компромисс:** нет continuous batching как в vLLM, но работает на CPU.

**Последствия:**
- флаг `--load-mode mmap+mlock` (новый API, старые `--mlock --no-mmap` удалены)
- `--parallel 2` для 2 одновременных запросов
- `--cont-batching` для лучшей утилизации

## ADR-003: Qdrant вместо pgvector

**Дата:** 2026-10-04
**Статус:** принято

**Контекст:** нужен векторный поиск по 384-dim эмбеддингам с фильтрацией по `project_id` и `document_id`.

**Решение:** Qdrant, режим low-memory.

**Альтернативы:**
- **pgvector** — проще, но медленнее с ростом данных
- **FAISS** — только in-memory, нет фильтров
- **Weaviate** — тяжелее, избыточно

**Компромисс:** +1 контейнер, но лучше по скорости и фильтрам.

**Последствия:**
- отдельный volume `qdrant_data`
- коллекция `project_documents`, Cosine, 384 dims
- payload-индексы на `project_id`, `document_id`
- **query_points()** вместо устаревшего search()

## ADR-004: multilingual-e5-small

**Дата:** 2026-10-04
**Статус:** принято

**Контекст:** русскоязычные документы + код, нужны быстрые эмбеддинги на CPU.

**Решение:** `intfloat/multilingual-e5-small`, 384 dims, ~120 МБ.

**Альтернативы:**
- **bge-small-en** — только английский
- **GigaEmbeddings** — 2 ГБ RAM, не влезает
- **rubert-tiny2** — слишком слабый
- **OpenAI Ada-002** — облако

**Компромисс:** компактная, работает с русским, но проигрывает SOTA на узких доменах.

**Последствия:**
- префиксы `query:` / `passage:` обязательны
- отдельный контейнер `nexus-embeddings`
- 384 dims синхронизированы с Qdrant

## ADR-005: API-first без встроенного UI

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** фронт — Laravel + Nest.js, разрабатывается отдельной командой.

**Решение:** NEXUS AI предоставляет только API. UI — минимальный отладочный на Nginx.

**Альтернативы:**
- **Встроенный React-UI** — связывает backend и frontend
- **Отдельный frontend-контейнер** — дублирует работу Laravel

**Компромисс:** +1 интеграционный слой (Laravel проксирует API NEXUS).

**Последствия:**
- CORS настроен под домены Laravel/Nest.js
- аутентификация — только API-ключи (без JWT, без сессий)
- пользователи и роли живут в Laravel
- OpenAPI / Swagger /docs за admin-ключом

## ADR-006: API-ключи вместо JWT

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** сторонние системы подключаются по HTTP. Нужна простая аутентификация.

**Решение:** два типа ключей — admin (в .env) и project (в БД).

**Альтернативы:**
- **JWT** — сложнее, для сессий пользователей
- **OAuth 2.0** — избыточно для внутренней системы
- **mTLS** — сложно разворачивать

**Компромисс:** нет ролей и гранулярных прав — они в Laravel.

**Последствия:**
- admin-ключ — plaintext в `.env`, полный доступ
- project-ключи — SHA-256 хеш в БД, привязаны к проекту
- allowed_experts ограничивает доступных экспертов
- rate_limit_per_min у каждого ключа

## ADR-007: PostgreSQL для структурированных данных

**Дата:** 2026-10-04
**Статус:** принято

**Контекст:** нужны ACID, FK, JSONB для гибких полей.

**Решение:** PostgreSQL 17.

**Альтернативы:**
- **MySQL** — хуже JSONB
- **MongoDB** — нет ACID на нужном уровне
- **SQLite** — не для нагрузки

**Компромисс:** стандарт, легко мигрировать.

**Последствия:**
- 15 таблиц
- триггер updated_at
- audit_log с JSONB
- `shared_buffers=2GB`, `work_mem=16MB`

## ADR-008: Чанкинг 500/100 с умным обрезом

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** RAG-поиск по документам. Нужен баланс между размером чанка и точностью.

**Решение:** 500 символов, overlap 100. Обрез по границам предложений (`. `, `\n\n`).

**Альтернативы:**
- **Фиксированный 512/128** — ломает предложения
- **По абзацам** — слишком крупно/мелко
- **По токенам** — требует токенизатор, сложнее

**Компромисс:** 3–5 чанков на короткий документ, 15–20 на средний.

**Последствия:**
- `MIN_CHUNK_SIZE = 50` — не создаём крошечные обрезки
- `MAX_CHUNKS_PER_DOC = 5000` — защита от бесконечных документов
- для коротких текстов (<50 символов) — 1 чанк

## ADR-009: Hot RAG-контекст в system_prompt

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** найденные чанки нужно передать модели.

**Решение:** добавляем RAG-контекст **в конец system_prompt**.

**Альтернативы:**
- Отдельным сообщением `role: system` после основного
- В user-сообщение как префикс
- Отдельным блоком `role: tool` (не поддерживается llama.cpp)

**Компромисс:** модель лучше следует инструкциям в system, чем в user.

**Последствия:**
- инструкции «Отвечай только по фрагментам» работают
- ссылки `[1]`, `[2]` в ответе
- каждый эксперт получает **тот же** RAG-контекст (в оркестрации)

## ADR-010: Фильтр документов в RAG

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** в проекте 10+ документов, пользователь хочет анализ одного.

**Решение:** параметр `document_ids: [...]` в /v1/chat и /documents/{id}/ask.

**Альтернативы:**
- Отдельный проект для каждого документа — избыточно
- Всегда искать по всему проекту — теряется точность

**Компромисс:** +1 параметр, но сильный UX-выигрыш.

**Последствия:**
- в Qdrant-фильтре — `MatchAny` по `document_id`
- отдельный эндпоинт `/documents/{id}/ask`
- в response — `sources` с `document_name`

## ADR-011: In-memory rate limiting

**Дата:** 2026-10-05
**Статус:** принято (временное)

**Контекст:** нужен rate limiting по API-ключу.

**Решение:** sliding window в памяти процесса.

**Альтернативы:**
- **Redis** — правильнее, но +1 контейнер
- **Nginx limit_req** — по IP, не по ключу
- **PostgreSQL** — слишком медленно для каждого запроса

**Компромисс:** работает только в рамках одного инстанса API.

**Последствия:**
- при горизонтальном масштабировании — заменить на Redis
- `/v1/admin/stats` не показывает текущее состояние счётчиков (можно добавить)

## ADR-012: SSE для стрима, не WebSocket

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** пользователь должен видеть печать в реальном времени.

**Решение:** Server-Sent Events.

**Альтернативы:**
- **WebSocket** — двунаправленный, но избыточно
- **Long polling** — медленно
- **HTTP chunked** — не стандартизовано

**Компромисс:** только сервер→клиент, но этого достаточно.

**Последствия:**
- `/v1/chat/stream`
- события: start, expert_start, reasoning, token, expert_done, done
- Nginx: `proxy_buffering off`
- клиент: fetch + ReadableStream

## ADR-013: Проксирование через Laravel

**Дата:** 2026-10-05
**Статус:** принято

**Контекст:** UI не должен видеть API-ключи NEXUS AI.

**Решение:** Laravel проксирует запросы UI → NEXUS AI.

**Альтернативы:**
- UI напрямую в NEXUS AI с API-ключом в localStorage — небезопасно
- Backend-for-frontend на отдельном сервисе — дублирует Laravel

**Компромисс:** +1 сетевой хоп, но безопаснее.

**Последствия:**
- ключи только на сервере Laravel
- UI работает через сессии Laravel
- SSE-проксирование требует `proxy_buffering off` на обоих уровнях
